# Architecture — Repo Layout & Where Code Goes

This document is the map. If you are about to create a file and don't know
where it belongs, the answer is here. If it genuinely isn't, add the rule here
in the same PR that adds the file.

## Top level

```
CLAUDE.md               agent constitution — stack, rules, boundaries (read first)
README.md               human quick start
contracts/              golden JSON fixtures pinning the API contract — backend
                        tests assert the real response equals the fixture
                        field-for-field; frontend schema tests parse the same file
docs/                   workflow · prd · design · architecture · components · task-workflow
  mockups/              disposable stage-2 prototypes — self-contained HTML,
                        never imported by frontend/src/ (created on first use)
  projects/             one design doc per project: components, requirements,
                        and the approved task list (created on first use)
frontend/               Vite + React 19 + TS strict (pnpm)
backend/                FastAPI + Pydantic v2 (uv)
.github/                workflows/: CI, the identical full gate on every PR ·
                        dependabot.yml: weekly grouped dependency bumps (the
                        gate is what makes merging them safe)
```

## Frontend (`frontend/`)

```
src/
  main.tsx              app bootstrap: QueryClient + Router providers only
  routeTree.gen.ts      generated by the router plugin on any vite command —
                        committed so a fresh clone typechecks; CI fails on drift
  routes/               TanStack Router file-based routes — THIN screens
  components/           domain components — one folder per component (docs/components.md)
    ui/                 primitives with zero domain knowledge
      Badge/            exemplar of the DEFAULT shape: presentational, args-only stories
    BackendStatus/      exemplar of the rare CONNECTED exception (hook + fetch stubs)
  hooks/                TanStack Query hooks — ALL server state goes through here
  lib/
    api-client.ts       the only place fetch() is called; parses with Zod schemas
    schemas.ts          Zod schemas mirroring backend Pydantic models (contract)
                        …plus pure UI logic as it lands — computed here,
                        rendered in components
  styles/
    index.css           Tailwind entry; design tokens as CSS variables
.storybook/             Storybook config (react-vite; reuses vite.config.ts)
scripts/                gate plumbing — depcruise.mjs runs the import fence and
                        fails on a vacuous pass (0 modules cruised = dead fence)
tests/
  setup.ts              Vitest setup (jest-dom matchers, Testing Library cleanup)
  unit/                 non-component unit tests mirroring src/ (schemas, lib,
                        hooks), plus the all-stories smoke loop (stories.test.tsx)
  e2e/                  Playwright acceptance tests — real UI, real backend
```

Placement rules:

- **Routes are screens, screens are thin.** Local UI state and wiring are
  fine; business logic and reusable markup are not — extract a component.
- **Components own their folder, in two tiers.** `src/components/ui/` holds
  domain-blind primitives; `src/components/` holds domain components whose
  props are schema types. Imports flow routes → domain → ui; composition
  within a tier goes through barrels; ui never imports domain and nothing
  imports routes. Enforced by `.dependency-cruiser.cjs` in the gate.
  Component tests and stories are co-located; everything else's unit tests
  mirror `src/` under `tests/unit/`.
- **Server state never lives in components.** Fetching goes
  `component → hook (src/hooks/) → api-client → Zod parse`. Components
  consume hook results or props; they never call `fetch` or build URLs.
- **The Zod ↔ Pydantic contract is sacred, and pinned from both sides.**
  Every backend response model has a Zod mirror in `src/lib/schemas.ts` and a
  golden fixture in `contracts/`: a backend test asserts the real endpoint
  response equals the fixture, and a frontend test parses the same fixture.
- **Theming is CSS tokens** in `styles/index.css` (raw values on `:root`,
  mapped into Tailwind via `@theme inline`, so an alternate theme is a
  selector swapping variables). Components never take palette props.
- Path alias: import from `@/…` (maps to `src/`), never relative `../../..`.

## Backend (`backend/`)

```
src/app/
  main.py               FastAPI app entrypoint — wiring only
  api/
    routes.py           HTTP layer — THIN; parse request, call module, shape response
  health/               exemplar domain package: routes delegate to modules like
    service.py          this one — one package per domain area, created on first use
  models/
    schemas.py          Pydantic models shared across the API (mirrored in frontend)
tests/
  conftest.py           shared fixtures (TestClient)
  unit/                 fast tests, mirror src/app/ (contract fixtures asserted here)
  integration/          real-server tests (uvicorn on ephemeral port, httpx)
```

Placement rules:

- **`api/routes.py` stays thin.** Any logic beyond parse/delegate/shape
  belongs in a dedicated module under `src/app/` — one package per domain
  area, created on first use, with tests mirroring under `tests/unit/`.
  `app/health/service.py` is the living exemplar of the shape: the route
  delegates to it, and `tests/unit/health/` pins it — copy that split for
  every new domain area.
- **External services go behind interfaces** (a `providers/` package) so
  tests never hit the network; e2e runs against fake provider adapters,
  which is backend configuration, not mocking.
- **Determinism boundary:** anything that decides money, time, scoring, or
  feasibility is plain unit-tested code. If an LLM enters the product, it
  touches intent and language only.

## API shape — decide resources early

Before building routes for a feature area, name its core resources and their
lifecycle **in this section**: what gets POSTed, what is addressable by id,
what survives a refresh, and which operations are mutations. Client-only
mutation state is not an API shape — anything a screen needs after a refresh
must live behind a GET. Record the decided shape here and pin its models in
`contracts/` as they land.

### Contract fixtures: dynamic fields and error shapes

Fixtures are compared to real responses field-for-field, which assumes the
response is deterministic. Keep it that way in this order:

1. **Make the backend deterministic under test.** Clocks, id generation, and
   randomness live behind provider interfaces (like external services below)
   and are pinned to fixed values in test configuration — the fixture stays
   exact and nothing is weakened.
2. **If a field truly can't be pinned**, assert its *format* separately
   (e.g. parses as ISO-8601), then overwrite it with the fixture's sentinel
   value before the equality check — in both the backend test and the
   frontend schema test. Never drop to subset matching; every field stays
   asserted, just one of them by shape instead of value.

Error responses: the moment the frontend branches on an error body (renders
a message from it, retries on a code), that error shape gets its own fixture
and Zod mirror like any other contract. Until then, FastAPI's default
`{"detail": …}` stays unpinned by design — the frontend treats non-2xx as
opaque failure.

## Deployment & runtime config (deferred on purpose)

The template ships no deployment shape — no Dockerfile, no CORS, no settings
module — because those are product decisions this repo can't make for you.
The homes are decided, though, so the first need doesn't improvise:

- **Runtime config**: the first env var lands in a `pydantic-settings` model
  in `src/app/config.py`, documented in `.env.example` in the same PR.
- **CORS**: unnecessary while the frontend reaches the backend through the
  dev-server `/api` proxy (and `vite preview` in CI e2e). Add middleware in
  `main.py` only when a deployment actually serves them from different
  origins — and record that deployment shape here when it's decided.

## Testing topology (who tests what)

| Layer | Tool | Location | Role in double-loop |
|---|---|---|---|
| User flows | Playwright | `frontend/tests/e2e/` | **Outer loop** — acceptance |
| API surface | pytest + httpx (real server) | `backend/tests/integration/` | Outer loop for backend-only work |
| Components | Vitest + Testing Library, composing stories | co-located in component folder | Inner loop |
| Component visual states | Storybook stories (setup source for tests) | co-located; smoke loop in `tests/unit/stories.test.tsx` | Inner loop; `build-storybook` in gate |
| Zod ↔ Pydantic contract | pytest + Vitest, shared fixtures | `contracts/` + tests on both sides | Inner loop |
| Domain logic | pytest | `backend/tests/unit/` | Inner loop |
| Import boundaries (tier rules) | dependency-cruiser | `frontend/.dependency-cruiser.cjs` | Gate — every PR |
| Lint + format (incl. the no-fetch-in-components fence) | Biome | `frontend/biome.jsonc` | Gate — every PR |

The workflow that drives this table is `docs/task-workflow.md`.
